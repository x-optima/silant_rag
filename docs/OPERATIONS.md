# Инструкция по эксплуатации сервиса

Документ для администратора, который обслуживает сервис на машине завода.
Развёртывание и удаление описаны в `README.md`; здесь — повседневная работа.

## 1. Что где находится

| Компонент | Адрес | Назначение |
|---|---|---|
| Чат | `http://<сервер>:8000/` | механик и оператор задают вопросы |
| Панель настроек | `http://<сервер>:8000/admin.html` | контакты службы, пороги, LLM |
| Проверка живости | `http://<сервер>:8000/api/health` | статистика базы, контроль мониторингом |
| Журнал | `docker compose logs -f silant-assistant` | ошибки разбора и ответов |

Доступ к панели: с самого сервера — без токена; с другого компьютера — по токену
из `.env` (поле «Токен доступа»).

## 2. Данные и их хранение

Всё состояние лежит на хосте в двух каталогах, которые смонтированы в контейнер
томами:

| Данные | Файл на хосте | Внутри контейнера |
|---|---|---|
| Настройки (контакты, пороги, правила) | `config/service.json` | `/app/config/service.json` |
| Индекс и реестр документов | `data/index.sqlite3` | `/app/data/index.sqlite3` |
| Исходные руководства | `data/documents/*.pdf` | `/app/data/documents/*.pdf` |
| Токен панели, режим, порт | `.env` | переменные окружения |

Что переживают операции:

| Операция | Настройки | Индекс | Документы |
|---|---|---|---|
| `docker compose restart` | сохраняются | сохраняются | сохраняются |
| `./destroy.sh` + `./deploy.sh` | сохраняются | сохраняются | сохраняются |
| `./deploy.sh --build` (пересборка образа) | сохраняются | сохраняются | сохраняются |
| `docker compose down -v` | сохраняются | сохраняются | сохраняются |
| `./destroy.sh --purge` | удаляются | удаляются | удаляются |

Причина: данные не лежат в образе и не являются docker-томом — это обычные
каталоги хоста. `--purge` перед удалением складывает их в
`backups/silant-backup-ГГГГММДД-ЧЧММСС.tar.gz`.

Внутри контейнера файловая система доступна только для чтения, поэтому запись
идёт исключительно в эти каталоги.

## 3. Ввод данных, которые раньше правились в JSON

Штатный способ — панель `/admin.html`. Файл `config/service.json` вручную
править не нужно: панель проверяет значения и применяет их сразу, без
перезапуска контейнера.

| Данные | Где вводить | Когда применяется |
|---|---|---|
| Название и подзаголовок в шапке чата | блок «Сервис» | сразу после сохранения |
| Телефон, почта, сайт службы, пояснение | блок «Контакты сервисной службы» | сразу |
| Пороги отказа (`min_coverage`, `min_score`, `min_matched_terms`, `top_k`, `candidate_limit`) | блок «Пороги отказа» | сразу |
| Модель, у которой второй ряд интервалов в скобках | селект «Модель с рядом в скобках» | сразу |
| Включение LLM, адрес API, модель, temperature, timeout | блок «LLM-режим» | сразу (ключ — отдельно) |
| Правила уточнения модели, границы применимости базы | блок «Полный JSON» | сразу |
| Ключ LLM | `.env`, переменная `SILANT_LLM_API_KEY` | после `./deploy.sh` |
| Токен панели | `.env`, создаётся `deploy.sh` автоматически | после `./deploy.sh` |
| Руководства | файлы в `data/documents` | после `./deploy.sh --reindex` |

Порядок правки настроек:

1. Открыть `http://127.0.0.1:8000/admin.html`.
2. Если страница закрыта (`403`) — вставить токен из `.env` в поле «Токен доступа»
   и нажать «Применить».
3. Изменить поля, нажать «Сохранить настройки».
4. Убедиться, что появилось сообщение об успехе, а не список ошибок.
   При ошибке файл не меняется.

Предыдущая версия файла сохраняется рядом как `config/service.json.bak`: если
правка сделана ошибочно, файл можно вернуть.

Проверка после правки: задать вопрос, ответа на который в руководствах нет, —
в ответе должен появиться указанный телефон службы вместо заглушки.

## 4. Загрузка и обновление руководств

PDF не вводятся через панель: это файлы. Порядок:

```bash
# 1. Положить или заменить файл
cp rukovodstvo-pd-pg.pdf data/documents/

# 2. Переиндексировать внутри контейнера
./deploy.sh --reindex

# 3. Проверить, что документ и таблицы распознаны
docker compose exec silant-assistant python3 -m app.ingest --list
```

`./deploy.sh` без флага индексирует только новые файлы: неизменившиеся
пропускаются по контрольной сумме. `--reindex` заменяет изменённые документы,
поэтому им пользуются при выходе новой редакции руководства.

Удаление устаревшего документа:

```bash
docker compose exec silant-assistant python3 -m app.ingest --drop <doc_id>
```

`doc_id` строится из имени файла и виден в выводе `--list`. После замены
редакции задайте несколько вопросов по обновлённому разделу и проверьте, что
значения и ссылки на страницы соответствуют новой редакции.

## 5. Ежедневная проверка

```bash
docker compose ps                                  # ожидается Up (healthy)
curl -s http://127.0.0.1:8000/api/health           # статистика базы
docker compose logs --tail=50 silant-assistant     # ошибки за последнее время
```

Признаки нормальной работы:

- контейнер в состоянии `healthy`;
- в `/api/health` число документов соответствует загруженным руководствам;
- в журнале нет повторяющихся ошибок разбора PDF.

Раз в неделю полезно проверить один вопрос с известным ответом и убедиться, что
сервис указывает тот же раздел, что и в руководстве.

## 6. Резервное копирование и восстановление

Копировать нужно два каталога и файл переменных окружения. Индекс копируется
при остановленном контейнере.

```bash
# копия
./destroy.sh --yes
mkdir -p backups
tar czf backups/silant-backup-$(date +%F).tar.gz data config .env
./deploy.sh --no-build

# восстановление на той же или новой машине
./destroy.sh --yes
tar xzf backups/silant-backup-2026-11-12.tar.gz
sudo chown -R 1000:1000 data config
chmod 600 .env
./deploy.sh
```

Индекс входит в архив, поэтому переиндексация после восстановления не нужна.
Если переносится только `config/`, сервис поднимется с пустой базой: документы
нужно скопировать отдельно и выполнить `./deploy.sh --reindex`.

## 7. Обновление приложения

```bash
# новые файлы кода
./deploy.sh

# принудительная переиндексация после изменения правил разбора
./deploy.sh --reindex
```

Правки в `app/` и `web/` попадают в контейнер только после пересборки образа:
`./deploy.sh` делает это автоматически. База и настройки при пересборке не
затрагиваются.

## 8. Действия при сбоях

| Симптом | Что проверить | Действие |
|---|---|---|
| страница не открывается | `docker compose ps` | `./deploy.sh`; при ошибке — журнал |
| контейнер перезапускается по кругу | `docker compose logs --tail=100` | чаще всего права на `data/`: `sudo chown -R 1000:1000 data config` |
| все ответы «ответа нет» | `--list`, `/api/health` | документы не загружены или пороги не подходят; выполнить `./deploy.sh --reindex`, при необходимости снизить `min_coverage` в панели |
| ответы по неверной модели | вопросы и регламент | проверить, указана ли модель; селектор модели в шапке чата |
| панель отвечает `403` | `.env` | вставить токен в поле «Токен доступа» или обновить его через `./deploy.sh` |
| таблицы в ответе искажены | вывод `--list` | сложная вёрстка PDF; для критичных таблиц сверять с документом вручную |
| настройки не сохраняются | сообщение панели | `422` — значение вне диапазона; исправить поле |

## 9. Ограничения эксплуатации

- у чата нет аутентификации: сервис рассчитан на локальную сеть завода;
- при публикации наружу нужен обратный прокси с авторизацией и HTTPS;
- панель настроек защищена токеном, но не заменяет разграничение доступа в сети;
- сервис не заменяет руководство: он ускоряет поиск раздела, решение принимает
  механик, сверившись с документом;
- графические схемы и нагрузочные диаграммы не индексируются.
